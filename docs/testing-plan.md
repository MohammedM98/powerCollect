# خطة الاختبار الكامل — PowerCollect

هذه الوثيقة هي المرجع لجولة الاختبار الكاملة: ما يُختبر، بأي أمر، بأي ترتيب، وما حدود التعديل. نتائج كل جولة تُكتب في `docs/testing-report.md`.

## 1. الهدف والحدود

- تشغيل كل طبقات المشروع، ثم حصر الثغرات، ثم كتابة الاختبارات الناقصة.
- **كود التطبيق لا يُعدَّل في الجولة.** الأخطاء ومخالفات المحدِّدات تُسجَّل في التقرير وتنتظر قرار المالك.
- اختبار يفشل بسبب خطأ حقيقي في الكود يبقى فاشلًا ويُذكر في التقرير. لا يُعطَّل اختبار ولا يُتخطّى ليصبح الناتج أخضر.
- العمل على الفرع المحدد للجلسة فقط، ولا يُفتح طلب دمج إلا بطلب المالك.
- **إذن قبل كل خطوة.** عند انتهاء كل خطوة: تُحدَّث «حالة التنفيذ» في `docs/testing-report.md`، يُدفع العمل، يُعرض ملخص النتيجة، ثم يتوقف العمل حتى يأذن المالك بالخطوة التالية. لا تُبدأ خطوة دون إذن صريح، ولو كانت السابقة ناجحة.
- **التنفيذ على أيام.** الجولة قد تمتد على عدة جلسات. كل جلسة تبدأ بقراءة «حالة التنفيذ» وتكمل من أول خطوة غير منتهية، دون إعادة ما انتهى.

## 2. المحدِّدات

1. **HeroUI فقط.** كل عنصر واجهة من `@heroui/react` (الإصدار 3) ومن عُدّة المشروع `@/Components/UI`. لا `<button>` أو `<input>` أو `<select>` خام، ولا مكتبة واجهات أخرى. المرجع الوحيد للمكوّنات: <https://heroui.com/en/docs/react/components>
2. **SOLID.** إلزامي على كل اختبار جديد (سلوك واحد لكل اختبار، إعادة استعمال المصانع والمساعدات، لا اعتماد على تفاصيل التنفيذ). على كود التطبيق: مراجعة وتقرير فقط.
3. **سلّم المسافات.**

   | الدرجة | القيمة | الوظيفة |
   |---|---|---|
   | `1` | 4px | بين أيقونة ونصّها |
   | `2` | 8px | بين عناصر متلاصقة داخل عنصر تحكم واحد |
   | `3` | 12px | بين حقول النموذج، وحشوة عناصر التحكم |
   | `4` | 16px | حشوة البطاقة وهامش الصفحة على الهاتف |
   | `6` | 24px | حشوة البطاقة والنافذة على سطح المكتب، وبين الأقسام |
   | `8` | 32px | بين مجموعات الصفحة الكبرى |

   - المسافة بين العناصر يضعها الأب بـ`gap`؛ المكوّن لا يحمل هامشًا خارجيًا.
   - اتجاهات منطقية فقط: `ps/pe/ms/me/start/end`.
   - لا قيم اعتباطية (`p-[13px]`) ولا درجات بينية (`1.5`، `2.5`، `3.5`، `5`، `7`).
4. **المهارات الملزمة.** `code-review`، `ponytail` (و`ponytail-audit`، `ponytail-review`)، `unslop`، `frontend-design`، `testing-best-practices`، `powercollect-check`، `laravel-best-practices`، `inertia-react-development`، `powercollect-review`، `security-review`.
   - `unslop` و`frontend-design` للتدقيق فقط: تصميم MA المعتمد في `CLAUDE.md` هو المرجع، ولا يُقبل تعديل بصري دون موافقة المالك.
   - `ponytail` يحكم كتابة الاختبارات: أصغر تغيير يحل المطلوب.
   - `code-review` يُشغَّل على فرق كل دفعة اختبارات قبل الـcommit.

## 4. الخطوات

كل خطوة تنتهي بتوقف وإذن (القسم 1). الخطوات 2 و4 كبيرة، فتُقسم إلى دفعات بحسب الجوانب، ولكل دفعة إذنها.

### 0. تجهيز البيئة

```bash
composer install --prefer-dist --no-interaction
cp .env.example .env && php artisan key:generate
npm ci && npm run build
```

- Flutter بالإصدار المثبَّت في `.github/workflows/tests.yml`، ثم `flutter pub get` داخل `mobile/`.
- خادم MySQL 8 لاختبارات المال والتقارير.
- ما يتعذّر تجهيزه يُذكر صراحة في التقرير مع السبب، ولا يُعدّ ناجحًا.

### 1. خط الأساس (قبل أي تغيير)

| الطبقة | الأمر |
|---|---|
| الفحص الثابت | `vendor/bin/pint --test`، `composer validate`، `npm run lint`، `npm run typecheck` |
| الباك إند | `php artisan test --compact` |
| منطق الواجهة | `npm test` |
| المكوّنات | `npm run test:components` |
| البناء | `npm run build` |
| المتصفح | `node tests/Browser/run.mjs` ثم مرة لكل راية: `--reports`، `--print`، `--distribution`، `--readings`، `--branches`، `--meter-boxes`، `--subscriber-navigation`، `--statement-actions` |
| MySQL | `vendor/bin/phpunit --filter` بنفس التعبير الموجود في مهمة `tests-mysql` في `.github/workflows/tests.yml`، مع متغيرات `DB_*` و`DB_URL` لـMySQL |
| الموبايل | داخل `mobile/`: `flutter analyze` ثم `flutter test --reporter expanded` |

مجموعات المتصفح تحتاج `public/build` و`vendor`، وتقبل راية واحدة في كل تشغيل.

### 2. جرد الثغرات

- **مصفوفة المسارات**: لكل مسار في `routes/web.php` و`routes/auth.php` و`routes/api.php` أربع حالات: زائر، بلا صلاحية، بصلاحية، فرع آخر. كل مسار ينتهي بحالة: مغطى، مستثنى (مع السبب)، أو ثغرة.
- **المصادقة**: كل سلوك في `LoginRequest`، `AuthenticatedSessionController`، `MobileSessionController`، `AuthenticateMobileToken`، `UserDeviceAccess` يقابله اختبار.
- **الواجهة**: مجلدات `resources/js/Pages` و`Components` التي لا اختبار لها.
- **المحدِّدات**: العناصر الخام خارج العُدّة، مطابقة المكوّنات مع توثيق HeroUI، مخالفات سلّم المسافات، مخالفات SOLID بالملف والسطر.
- **التدقيق**: `ponytail-audit`، `security-review`، `unslop`.
- **التشغيل**: ما لا يشغّله CI ولا `npm run check`.

### 3. التقرير الأول

`docs/testing-report.md` مرتبًا بالخطورة، ثم توقف لقرار المالك.

### 4. كتابة الاختبارات الناقصة

بالأولوية، وكل اختبار يُشغَّل فور كتابته:

1. اختبار اصطلاحي يمرّ على كل المسارات: الزائر يُحوَّل للدخول (ويب) أو يأخذ 401 (موبايل)، مع قائمة استثناءات صريحة للمسارات العامة.
2. سلوكيات المصادقة الناقصة.
3. اختبارات 403 وعزل الفروع للمسارات غير المغطاة، ومفاتيح `can.*`.
4. اختبارات مكوّنات لعُدّة `UI` و`DataTable` والصفحات المالية.
5. مجموعة متصفح للمصادقة والصلاحيات.
6. عقد الموبايل للمسارات التي يستعملها التطبيق فعلًا.

يُعاد استعمال: حالات `UserFactory` و`withPermissions()` (المصنع يمنح صلاحيات الدور تلقائيًا، فالمستخدم بلا صلاحيات يحتاج `permissions()->sync([])`)، `Permission::idsFor()`، `MobileAccessToken::issue()`، و`tests/Feature/Lifecycle/SetsUpCompanyThroughTheWebsite.php`. اختبارات PHP تُنشأ بـ`php artisan make:test --phpunit`.

### 5. إعادة التشغيل الكامل

كل أوامر الخطوة 1، ثم `vendor/bin/pint --dirty --format agent`. تُقارن النتائج بخط الأساس.

### 6. الفحص البصري

لقطات للصفحات الأساسية في فاتح/داكن، زجاجي/مصمت، وعرض الهاتف.

### 7. التثبيت الدائم (كل بند بموافقة صريحة من المالك)

إصلاح فروع التشغيل في `tests.yml`، إضافة مجموعات المتصفح وقياس التغطية إلى CI، قاعدة ESLint للعناصر الخام وسلّم المسافات، وأمر واحد يشغّل كل الطبقات.

### 8. التسليم

commit و push على فرع الجلسة، والتقرير النهائي.

## 5. معايير النجاح

- جدول نجاح/فشل لكل طبقة قبل الجولة وبعدها، بأعداد الاختبارات.
- لا مسار بلا حالة في مصفوفة المسارات.
- كل اختبار جديد يفشل حين يغيب السلوك الذي يحميه.
- كل ما تعذّر تشغيله مذكور بسببه.

## 6. البرومبت (لجلسة Claude جديدة)

```text
أنت تعمل على مستودع PowerCollect (Laravel + Inertia/React + تطبيق Flutter في mobile/).
نفّذ جولة الاختبار الكاملة الموصوفة في docs/testing-plan.md، واقرأ ذلك الملف و CLAUDE.md
و .ai/rules/index.md قبل أي شيء.

القواعد:
1. لا تعدّل كود التطبيق (app/، routes/، resources/، mobile/lib/، database/). المسموح:
   ملفات اختبار جديدة و docs/testing-report.md. أي خطأ أو مخالفة تجدها سجّلها في التقرير
   بالملف والسطر، ولا تصلحها.
2. لا تعطّل اختبارًا ولا تتخطّه ولا تضعف تأكيدًا ليصبح الناتج أخضر. الاختبار الذي يكشف خطأ
   حقيقيًا يبقى فاشلًا ويُذكر في التقرير.
3. التزم بالمحدِّدات الأربعة في القسم 2 من الخطة (HeroUI من موقعها الرسمي فقط، SOLID،
   سلّم المسافات، المهارات الملزمة). unslop و frontend-design للتدقيق فقط دون تعديل بصري.
4. فعّل المهارة المناسبة قبل العمل في مجالها: testing-best-practices قبل كتابة أي اختبار،
   laravel-best-practices لـPHP، inertia-react-development لـReact، ponytail لحجم التغيير،
   code-review على الفرق قبل كل commit.
5. اعمل على الفرع المخصص لجلستك فقط، ولا تفتح طلب دمج.
6. خطوة واحدة في كل مرة. ابدأ بقراءة جدول «حالة التنفيذ» في docs/testing-report.md، وأخبر المالك
   بأول خطوة غير منتهية واطلب إذنه قبل بدئها. عند انتهائها: حدّث الجدول، ادفع العمل، لخّص
   النتيجة، وتوقف. لا تبدأ الخطوة التالية دون إذن صريح، ولا تعد تنفيذ خطوة منتهية.

الخطوات (التفاصيل في القسم 4):
- 0: تجهيز البيئة. ما يتعذّر (Flutter، MySQL) اذكره بسببه. البيئة تُجهَّز من جديد في كل جلسة
  دون إذن، لأنها لا تبقى بين الجلسات.
- 1: خط الأساس: كل طبقة كما هي، بالنتيجة والأعداد.
- 2: جرد الثغرات في الجوانب الأربعة والعشرين (القسم 3) ومصفوفة المسارات، على دفعات.
- 3: التقرير الأول مرتبًا بالخطورة، وقرار المالك فيما يُكتب.
- 4: كتابة الاختبارات الناقصة، على دفعات بحسب الجانب.
- 5: إعادة التشغيل الكامل والمقارنة بخط الأساس.
- 6: الفحص البصري.
- 7: التثبيت الدائم، كل بند بإذنه.
- 8: التسليم.

التقرير بالعربية، مختصر، بجداول: الطبقة، الأمر، النتيجة، العدد؛ ثم الثغرات؛ ثم الأخطاء
المكتشفة؛ ثم مخالفات المحدِّدات؛ ثم ما تعذّر تشغيله.
```
