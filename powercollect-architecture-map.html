PowerCollect Architecture Map

A complete map of the electricity collection system in mohammedm98/powerCollect: how it is built, how a request and a business week move through it, every database table with its relationships, every route and permission, and an honest assessment of what is strong and what needs work. Everything here was read from the code at commit 81ed955; the schema was produced by running all 92 migrations.

1 · Summary

What PowerCollect is

PowerCollect runs a small electricity company that sells power to subscribers through metered meter boxes (طبلونات) spread over governorates, areas and sub-areas, each served by a branch. Its job is the weekly cycle of the business: read every meter, turn the consumption into a charge on the subscriber's account, collect the money in the field or at the branch, keep each collector's cash box honest, close the week, audit it, report it, and chase or disconnect subscribers who do not pay.

Two clients, one Laravel core

  • Website (React pages served by Inertia): the office. Dashboard, subscribers and statements, readings and approvals, payments and cash boxes, closings and audit, reports, disconnection lists, SMS campaigns, printing, settings, users and permissions.
  • Field app (Flutter, Android): the collector and meter reader. Download assigned boxes, take readings offline (with receipt OCR), upload them, collect payments, split payments, send messages, see and close their own cash boxes.
  • Background: a scheduler that closes periods every minute, prepares the next reading week hourly and backs up nightly; a database queue that sends SMS; database notifications shown in the site's bell.

Design principles visible in the code

  • The ledger is append-only. A money line is never edited or deleted; it is cancelled with a reversal line and, when corrected, replaced by a new line that points back (corrects_id).
  • Everything belongs to a branch. A trait scopes every list to the user's branch; Super Admin sees all; optional per-branch sub-domains lock staff to their branch's link.
  • Permissions, not roles. 98 fine-grained permission keys are granted per user (roles are only starter sets), with delegation and an audit-only mode.
  • Money is exact. All amounts are decimal columns handled with brick/math; shekel is the book currency, other currencies are converted at the recorded rate.
  • Idempotent writes. Web payments carry a token and fingerprint, mobile uploads carry an operation id, so retries never double-record.
  • Arabic first. UI, messages and error pages are Arabic; the field app is RTL with Arabic fonts.

Verdict in one paragraph

This is a serious, well-tested line-of-business system with unusually careful financial invariants for a project of its size. Its main debts are structural rather than functional: very large model and controller classes, business logic spread across three layers, hard-coded Arabic copy inside PHP, schema left over from retired closing features, and an all-on-the-database infrastructure that will need a cache and a queue backend as data grows. The detailed list, with evidence and suggested fixes, is in section 9.

2 · Architecture

Layers and where the code lives

Read top to bottom: a click in the browser or a tap in the field app crosses each layer once on the way in, and the response crosses them on the way out. Code paths are relative to the repository root.

Backend shape (app/)

Controllers
73 web + 10 mobile + 3 auth. Thin for CRUD resources, thick for payments, readings, reports and disconnections (several over 400 lines).
Form Requests
82 classes in app/Http/Requests do validation and most authorize() calls. 33 controllers still validate inline.
Policies
29 policies map permission keys and branch membership to model actions; auto-discovered by Laravel.
Models
62 Eloquent models. Two traits: BelongsToBranch (branch relation + visibleTo scope) and OverridableByBranch (company default row + per-branch override rows for settings).
Support
34 service classes: closing workflow, reading allocation and sync, reports, money, branding, messaging gateway, backups. This is the real domain layer.
Enums
30 backed enums for every status, type and permission key.
Middleware
10: branch domain and view resolution, account active, device limit, auditor access, mobile token, mobile min build, security headers, Inertia shared props.
Console
8 commands: closings:process, readings:prepare-distributions, backup:run, subscriptions:import, brand:import/export/reset/options.

Frontend shape (resources/js/)

Pages
194 files under Pages/ in 24 folders; Inertia resolves Pages/{Name}.jsx lazily, one chunk per page. Forms and modals are co-located with their page and excluded from route-level splitting.
Components
102 shared components: DataTable, Form, Print, Charts, SideNavigation, TopBar, CommandPalette, ExcelStudio, HoldToConfirm, KpiTile…
Layouts
AuthenticatedLayout (rail + top bar), GuestLayout, SettingsLayout.
Hooks / lib
15 hooks (data tables, brand, theme, forms) and 58 pure modules in lib/ (statement maths, balance, currency, print layout, Excel export). The pure modules are what the 66 Node unit tests cover.
Styling
Tailwind 3 with a token theme (resources/css/theme.css), light/dark, company brand palette injected at runtime by app/Support/Brand.php.
Heavy client libs
exceljs for Excel export, pdfjs-dist for reading uploaded company forms.

Mobile app shape (mobile/)

Flutter 3.47, Dart, one package with 38 files in lib/ and 26 widget/unit tests. api_client.dart is the only network layer and talks to /api/mobile/* with a Bearer token and an X-PowerCollect-Build style header; field_store.dart persists session, queued readings and drafts to a JSON file in the app's files directory; queued_readings.dart and reading_flow.dart implement offline capture and later sync; receipt_scan.dart uses ML Kit text recognition to read bank receipt numbers. Pages: login, reading assignments, weekly readings, reading distribution (supervisor), collection view, subscriber page and history, payment, split payment, adjustment, cash boxes, message subscribers.

Background life

Scheduler (cron every minute)

  • closings:process every minute: for each branch whose closing workflow has started, BranchClosingWorkflow::refresh seals periods whose cut-off passed and opens the next one.
  • readings:prepare-distributions hourly: builds the coming week's reading cycle from the standing distribution (reading_distributions).
  • backup:run daily 02:30: database dump + private and public upload archives, verified, shipped to BACKUP_DISK, pruned after 14 days.

Queue (database driver)

  • SendSubscriptionMessage is the only job: 3 tries, backoff 60 s then 300 s, calls the bound SmsGateway (HTTP provider from sms_settings, or the log in development).
  • A message batch's rows move pending → sent / failed; a batch can be retried; WhatsApp rows are marked sent by hand.

Notifications & sessions

  • Database notifications (ActionCompleted, BranchClosingNotification, ReadingNeedsReapproval) feed the bell in the top bar; POST /notifications/read clears them.
  • Sessions, cache and cache locks all live in MySQL tables; the per-branch lock used around money writes is a cache lock.
  • GET /auth/session lets the page poll whether the session is still alive and warn before it expires.

Deployment life cycle

  1. Install: composer run setup (install, key, migrate, npm build). Seeders create the Super Admin from SUPER_ADMIN_* env, permissions, banks, currencies, tariffs, locations, a sample branch (مخيم 2) with users and subscribers.
  2. Deploy: HTTPS only, config:cache route:cache view:cache, migrate --force, queue:restart; one cron line runs the scheduler; supervisor keeps queue:work alive.
  3. Branding: the maker ships a company identity JSON (brand:import); the in-app appearance editor is behind BRAND_EDITOR_ENABLED.
  4. Branch links: with BRANCH_DOMAINS_ENABLED, each branch gets its own host; staff sessions on the central host are ended.
  5. Field app release: build the APK with API_BASE_URL, raise pubspec.yaml version and appBuildNumber, publish the link in MOBILE_APP_URL, and raise MOBILE_APP_MIN_BUILD when the API contract changes so old apps get a 426 "update" response instead of breaking.
  6. Operate: nightly backups, restore drill documented in README, CI runs PHP 8.3–8.5 matrix, Node tests + production build, and Flutter analyze + tests on every push.
